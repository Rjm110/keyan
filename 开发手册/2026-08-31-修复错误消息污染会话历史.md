# 修复：错误消息污染会话历史导致 deepseek 400 报错（2026-08-31）

> 开发内容：修复"配置真实 deepseek key 后发送消息报 `Invalid assistant message: content or tool_calls must be set`"的问题。
>
> 开发时间：2026-08-31

---

## 一、问题现象

用户在前端配置真实 DeepSeek API key 后发送"你好"，收到错误：

```
❌ [deepseek/deepseek-v4-flash @ https://api.deepseek.com] ProviderBadRequest:
Error code: 400 - {'error': {'message': 'Invalid assistant message: content or
tool_calls must be set', ...}}
```

## 二、根因分析

1. **错误消息被持久化**：之前用**假 qwen key** 测试时，每次发送消息，agent 都会把 `stop_reason="error"`、`content=[]` 的**空 assistant 错误消息**持久化到 SQLite checkpointer（`workspace/sessions.db` 的 messages 表）。
2. **历史恢复后发给模型**：用户配置真实 deepseek key 后再次发送，agent 从 checkpointer 恢复历史，把这些**空的 assistant 消息**（无 content、无 tool_calls）发给 deepseek → deepseek 报 `Invalid assistant message: content or tool_calls must be set`。

数据库证据（`workspace/sessions.db`）：
```
id=2:  {"role": "assistant", "content": [], "stop_reason": "error", "error_message": "[qwen/qwen-max @ ...] ProviderAuthFailed: Error code: 401 - ..."}
id=4:  {"role": "assistant", "content": [], "stop_reason": "error", ...}
...（共 12 条空错误消息）
```

## 三、解决方案

### 3.1 应用层过滤（app/agent_factory.py）

新增 `_convert_to_llm` 函数，在消息发给模型前过滤掉空的错误 assistant 消息：

```python
def _convert_to_llm(messages: list[Message], *, ctx: AgentContext) -> list[Message]:
    """过滤掉空的错误 assistant 消息（stop_reason=error 且无内容）。"""
    del ctx
    return [
        m
        for m in messages
        if not (
            isinstance(m, AssistantMessage)
            and m.stop_reason == "error"
            and not m.content
        )
    ]
```

通过 `Agent(convert_to_llm=_convert_to_llm, ...)` 传入。

### 3.2 清理数据库（一次性）

备份 `workspace/sessions.db` → `sessions.db.bak`，删除 12 条空的错误 assistant 消息（保留 user 消息）。

## 四、验证方式

1. **过滤逻辑验证**：用假 key 连续发 2 条消息，检查数据库——错误消息仍被持久化（cubepi 行为），但 `convert_to_llm` 过滤后只剩 user 消息发给模型，不再报 `content or tool_calls must be set`。
2. **真实 key 端到端验证**：用户配置真实 deepseek key 后发送"你好"，DeepSeek 正常回复（工作流程介绍），无 400 错误。
3. **静态检查**：`uv run mypy app/`（0 错误）、`uv run ruff check app/`（全过）、`uv run pytest app/tests/ -q`（14 passed）。

## 五、问题与解决

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 配置真实 key 后报 `content or tool_calls must be set` | 之前假 key 测试产生的空错误 assistant 消息被持久化，恢复历史后发给模型 | `convert_to_llm` 过滤 + 清理数据库 |

## 六、下一步

1. **错误消息不持久化**（更彻底的方案）：考虑在应用层 hook `_process_event` 或 checkpointer 层跳过 `stop_reason="error"` 的空消息持久化，避免历史污染。
2. **配置持久化**：运行时配置目前是内存存储，服务器重启后需重新配置 → 可落盘（如 `~/.cubepi/config.json`）。
